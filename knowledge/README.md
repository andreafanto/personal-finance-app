# Working Memory (`knowledge/`)

The harness's long-term memory. Dialogue skills (`/define-problem`,
`/requirements`, `/architecture-session`, `/design-frontend`) surface
domain knowledge in conversation. Without this folder that knowledge
disappears when the conversation ends. Here it becomes small, typed,
LLM-readable files that every later session and agent can load.

- **Write** with `/remember` (or at the capture step every dialogue skill
  runs before it ends).
- **Read** with `/recall <topic>`. Every skill also reads the index at
  boot-up.
- **Index**: `knowledge/INDEX.md` has one line per entry, generated by
  `python3 .harness/rebuild_index.py`. Do not edit it by hand. The same
  data is in `.harness/knowledge.json` for scripts.

## What goes where

| It is a...                                              | Store it as                  |
|---------------------------------------------------------|------------------------------|
| Meaning of a domain word ("rollover", "payee")          | `kind: term`                 |
| Business/domain invariant ("a category has 0-1 parent") | `kind: rule`                 |
| Style guide / code / naming / UX writing convention     | `kind: convention`           |
| Non-functional or scope limit ("single currency")       | `kind: constraint`           |
| Context about the user or environment                   | `kind: fact`                 |
| A choice between real alternatives, with rationale      | **ADR** in `architecture/ADRs/` (not here) |
| What the system must do for one problem                 | the requirement file (not here) |

Rule of thumb: if you would say "we *chose* X over Y", it is an ADR. If
you would say "X *is* true / X *means* Y / always do X", it is a
knowledge entry. The index lists both, so a reader has one place to look.

Do not copy things that already live elsewhere (CLAUDE.md, a requirement,
an ADR). Link to them with `related` instead.

## File format

`knowledge/kn-NNNN-short-slug.md`. The number is sequential and never
reused. Frontmatter stays flat (scalar `key: value` only), like everywhere
else in the harness.

```markdown
---
id: kn-0001
type: knowledge
kind: rule
title: "Budget rollover carries unspent amount only"
summary: "At period end, a category's unspent budget adds to next period's limit; overspend does not reduce it."
status: active
source: req-003
created: 2026-09-29
updated: 2026-09-29
tags: budget, rollover
related: req-003, kn-0002
supersedes: ""
superseded_by: ""
---

# Budget rollover carries unspent amount only

At the end of a budget period, if rollover is on for a category, the
unspent part of its limit is added to the next period's limit. Overspend
is not carried forward as a deduction.

**Why:** The user wants rollover to reward saving, not punish one bad month.
Said in the /requirements interview for req-003.

**How to apply:** Rollover math lives in the budget calculation, never in
the stored limit. Tests for req-003 must cover the overspend case
(carry = 0, not negative).

**Example:** Limit 300, spent 250 -> next period 350. Spent 320 -> next period 300.
```

### Fields

| Field           | Required | Notes |
|-----------------|----------|-------|
| `id`            | yes | `kn-NNNN`, must match the filename prefix |
| `type`          | yes | always `knowledge` |
| `kind`          | yes | `term`, `rule`, `convention`, `constraint`, `fact` |
| `title`         | yes | short, specific |
| `summary`       | yes | the fact itself in one sentence, at most 200 chars. This is what the index shows, so it must make sense alone |
| `status`        | yes | `active`, `superseded`, `retracted` |
| `source`        | yes | where it came from: an item id (`req-003`, `adr-0002`) or `session YYYY-MM-DD /<skill>` |
| `created`, `updated` | yes | `YYYY-MM-DD` |
| `tags`          | no  | comma-separated, lowercase. Reuse existing tags (see the index) before you add new ones |
| `related`       | no  | comma-separated ids (`kn-`, `adr-`, `req-`, `prob-`). Each one must exist |
| `supersedes`, `superseded_by` | no | see lifecycle |

### Body

1. One short paragraph that states the knowledge plainly and precisely.
2. `**Why:**` the reason, and who said it or where it came from. This lets
   a later reader judge edge cases instead of following the rule blindly.
3. `**How to apply:**` what it changes for requirements, tests, code, or UI.
4. Optional `**Example:**`. Examples are the best disambiguator for terms
   and rules.

Keep an entry to one fact. If you need "and also", write two entries and
link them.

## Lifecycle

- Entries are written **only after the user confirms them**. A guess
  stays in the conversation or goes into a file's "Open questions". It
  never goes into memory.
- **Changed knowledge:** write a new entry with `supersedes: kn-OLD`. Set
  the old one to `status: superseded`, `superseded_by: kn-NEW`. Never
  rewrite the meaning of an existing entry in place (small wording fixes
  are fine).
- **Wrong knowledge:** set `status: retracted` and add a line to the body
  saying why. Do not delete the file, because other items may cite the id.
- Retired entries stay in the index under "Retired", so a reader can see
  that an idea was considered and dropped.

`python3 .harness/rebuild_index.py --check` validates all of the above
(required fields, kinds, id/filename match, links resolve, supersede
links are symmetric) and exits non-zero on any error.
